# Events

Services publish events to atc-webhook-out (`POST /v1/events`, a key with the `publish` role). Anything that wants to react subscribes there: webhook-out owns subscriptions, signing, retries and replay. Publishing is best effort and never blocks the caller: each service keeps a bounded in-memory queue (500) and sends in the background with up to three retries and an idempotency key (`<service>:<uuid>`). A restart loses what is still queued, and a full queue drops the oldest event. Where an event must survive a crash, the service has its own outbox (atc-payments) or relies on the audit log.

`npm run setup` gives every publishing service `WEBHOOK_OUT_URL` and `WEBHOOK_OUT_API_KEY` (one `publish` key each, so a leaked key can publish and nothing else).

## Operational events (`ops.*`)

These mean "a person should look". webhook-out delivers every `ops.*` event to atc-status through the seeded subscription `alert-hub`; atc-status turns each into an alert, e-mails the first of a kind through atc-notify and counts repeats. The secret of that subscription is `ALERT_HOOK_SECRET` (generated by setup, in the `.env` of both services).

| Event | Publisher | When | Severity |
|---|---|---|---|
| `ops.backup.failed` | atc-backup | A backup, or its upload to media, failed | critical |
| `ops.backup.stale` | atc-backup | No successful backup of a source for two intervals | critical |
| `ops.queue.dead_letter` | atc-queue | Dead letters of a queue grew since the last maintenance run | warning |
| `ops.queue.dead_expired` | atc-queue | Retention removed dead letters | warning |
| `ops.scheduler.job_failed` | atc-scheduler | A run ended `failed` (not for attempts that will retry) | warning |
| `ops.webhook.subscription_disabled` | atc-webhook-out | A subscription was disabled after repeated failures | warning |
| `ops.audit.denied_spike` | atc-audit | One source stored many `denied` events in a short window | warning |
| `ops.payments.outbox_dead` | atc-payments | A payment event used up its delivery attempts | critical |

## Domain events

For systems that react to a change. They carry identifiers and never personal data or secret values.

| Event | Publisher | Data |
|---|---|---|
| `flag.changed` | atc-flags | `key`, `env`, `action`, `actor` |
| `content.release.published`, `content.release.rolled_back` | atc-content | `namespace`, `release`, `by` |
| `auth.user.created`, `.disabled`, `.enabled`, `.deleted` | atc-auth | `id` |
| `incident.opened`, `incident.closed` | atc-status | `id`, `monitor`, `name`, `cause`, `failures` |
| `backup.completed` | atc-backup | `source`, `id`, `size`, `sha256` |
| `payment.*`, `refund.*` | atc-payments | see its `examples/events.md` |

## Subscribing

Create a subscription in webhook-out (console: Webhooks) with a URL and event patterns (`ops.*`, `flag.changed`, `*`). Deliveries are signed with the subscription secret; verify them as in `atc-webhook-out/examples`. atc-status shows how: `AlertService.receive` checks the signature against the raw body and rejects stale timestamps.

## Watching the publishers

Every publisher exposes `events_publish_enabled`, `events_publish_total{result="published|sent|dropped|failed"}` and `events_publish_pending` on `/metrics`. A rising `dropped` or `failed` means events are being lost; the cause is nearly always webhook-out being down or a key without the `publish` role.
